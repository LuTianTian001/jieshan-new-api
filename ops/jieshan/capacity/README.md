# 介山 New API · 1000 条文本流容量验收

这里的 1000 并发指 1000 条已经开始返回正文、同时还没结束的 Chat Completions 流。平均每条持续 30 秒，维持 1000 条约需每秒新开 33 条（2000 RPM）。若目标是每秒新开 1000 条、每条持续 30 秒，则是约 3 万条同时在途，需另一套验收。

## 为什么这样分配

主机有 16 个 vCPU、约 15.6 GiB 内存。旧网关保留原有 6 vCPU / 4 GiB 上限。新服务的上限合计 8.5 vCPU / 6.5 GiB，容器仅按需使用；主机和其他服务仍需共享剩余资源。第一次容量测试按应用 6 核、数据库 2 核分配，总额相同。1000 并发三轮完整返回，应用采样峰值 2.22 核且没有 CPU 限速；PostgreSQL 在集中结算的阶段有 51 个调度周期碰到上限。因此把一核从应用挪给数据库，再在最终配置上复测。

| 服务 | CPU / 内存上限 | 设置考虑 |
|---|---|---|
| New API | 5 vCPU / 4 GiB | 流式转发、JSON、长输入及请求缓冲。Go 运行时软内存目标为 3 GiB，剩余空间供套接字、文件页等使用。 |
| PostgreSQL | 3 vCPU / 2 GiB | 结算、配额、消费日志；同一账户或同一 Key 还可能发生行锁竞争。应用池最多 64 个连接、闲置最多 16 个，低于 PostgreSQL 自身的 100 个连接上限。 |
| Redis | 0.5 vCPU / 512 MiB | 缓存和限流，应用连接池 32 个。没有更改正式站点的限流和计费策略。 |

## 2026-11-26 实测

同一台介山主机的独立副本；上游是模拟服务。测试期间旧网关在线，但未模拟旧网关业务高峰。以下是最终 5 / 3 / 0.5 核配置的结果，详见[测量记录](2026-11-26.jsonl)。

| 1000 并发场景 | 完整返回 | 客户端实测满并发时长 | 首段正文 P95 / P99 | New API 采样内存峰值 |
|---|---:|---:|---:|---:|
| 每条约 30 秒，连续三轮 | 3000 / 3000 | 三轮合计 72.76 秒 | 149.88 / 161.40 ms | 342.9 MiB |
| 每条约 5 分钟，约 48 KiB 请求体 | 1000 / 1000 | 连续 293.11 秒 | 114.74 / 120.69 ms | 691.1 MiB |

加上各档预热共有 5001 次完整请求、5001 个唯一消费请求 ID。账户和 Key 的余额均减少 12,276,032 个测试额度，与日志合计一致。旧网关 522 次健康采样全部成功，P95 为 1.54 ms；测试前后容器 ID、启动时间和重启次数均一致。最终配置中应用和数据库没有 CPU 限速记录；全机 CPU 采样最高 29.3%，可用内存最低约 13.5 GiB。本次首段正文时间含模拟上游的出字节奏，不代表真实供应商的响应时间。

## 怎样验收

服务镜像和容量配置取自部署目录。另建一个 `js-capacity-*` 项目，只使用内部 Docker 网络，不映射端口。PostgreSQL、Redis、管理员、Key、价格和消费记录都是本轮独立创建的，不读写真实业务数据。两个受限的 Python 容器分别发送客户端请求和模拟 OpenAI SSE 上游。客户端从第一段非空正文开始记录实际重叠的流，同时从模拟上游独立读取峰值。

- 先测 1、100、300、600，再起 1000 个客户端。最后一档在 6 秒内升至 1000，每个客户端连续发 3 条，每条约 30 秒、每秒 10 段正文。逐条校验完整内容、停止原因、上游 usage 和 `[DONE]`。本机首段正文 P95 门槛为 1 秒。
- `--with-soak` 加测 1000 个客户端：每条约 48 KiB 输入、持续约 5 分钟、返回 3000 段正文。客户端实测同时收正文的时间必须至少 255 秒。这里的 8192 输入 token 是模拟上游返回的账务测试值，不是对真实文本 tokenizer 的测量。
- 每档统计唯一请求 ID 和消费日志，核对账户余额、受限 Key 余额、测试扣费。每秒左右采样真实旧网关健康端点、主机资源和容器 cgroup 数据（内存含缓存，CPU 峰值为采样区间均值）。旧网关连续两次健康检查失败或超 500 ms、可用内存低于 3 GiB、主机 CPU 连续三次超 85%，或试验容器 OOM 时中止并清理副本。

在介山主机有空余时，从部署包根目录运行。需要 Linux/cgroup v2、Python 3、支持 `!reset` 的 Docker Compose（2.24.4+），同机已有健康的 `jieshan` 容器和回环 4000 健康端点。预先拉取部署 Compose 的三个固定镜像和 `compose.test.yaml` 指定的 Python 镜像。验收只使用已有的本机镜像。

```bash
set -o pipefail
python3 -B capacity/verify.py --with-soak | tee capacity-result.jsonl
```

看到 `pass` 后还要看到 `cleanup`、`project_removed: true` 和 `sibling_identity_unchanged: true`。项目名随机生成；脚本只清本次测试创建的容器、数据卷、网络和临时目录。日常访问、发布和回退沿用[部署说明](../README.md)，不启动容量测试容器。

## 商售前还要测什么

这套验收覆盖同机 New API 的转发和账务。公网 TLS、反代是否缓冲 SSE、出口带宽、真实供应商并发/RPM/TPM 限额及高峰冷启动延迟会改变结果。按实际模型与上下文测一遍，区分上游 429、本站 503、断流与超时。以平均 30 秒、每条共 1200 token 为例，1000 条并发需要上游合计约 2000 RPM、240 万 TPM，还应为流量波动、降级时的备用渠道留出容量。分销套餐应按已验收的供应商额度和峰值来定。
